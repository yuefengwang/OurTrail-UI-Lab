OurTrail Visual Direction Lab：多风格 UI 探索与全局设计系统建设

0. 任务定位

你正在参与 OurTrail 开源户外活动协作小程序的新一轮 UI 重构。

项目仓库："https://github.com/yuefengwang/OurTrail"

本任务不是直接重做所有生产页面，而是先在现有项目基础上建设一个 Visual Direction Lab（视觉方向实验室），通过可运行的多风格 UI 原型，确定产品未来的视觉方向，再为后续全局设计系统建设和逐页重构提供可靠依据。

产品期望气质：

- 高级、克制、有鲜明品牌辨识度。
- 真实、成熟、可信赖，不像 Demo、模板站或概念设计稿。
- 具有户外产品特征，但不依赖简单的山峰图标、绿色渐变和大量山景照片表达户外属性。
- 兼顾活动发现的吸引力、协作页面的操作效率，以及地图和天气页面的信息密度。
- 适合长期迭代的微信小程序，而不是只在一张静态截图中好看。

本阶段最重要的交付物是一个可运行、可比较、与生产代码隔离的多风格原型，以及基于实际代码审计形成的后续实施方案。

不得将本任务理解为立即重构整个小程序。

---

1. 总体工作原则

1.1 先审计，再设计

必须先读取真实仓库、当前分支、页面结构、组件实现、全局样式、设计令牌和已有测试。

不得只根据 README、旧截图、印象或想象出来的页面进行设计。

重点识别：

- 当前有哪些真实页面、页面路由和核心用户流程。
- 页面之间复用哪些组件，哪些页面存在重复实现。
- 全局样式、页面级样式和组件样式之间的关系。
- 当前视觉问题究竟来自色彩、排版、留白、组件形态、信息层级、图片、图标，还是页面结构。
- 哪些组件承载业务状态和交互逻辑，不能在视觉实验中被破坏。
- 哪些已有页面已经具备较好的设计基础，值得保留。
- 当前自动化测试、开发者工具和视觉验收能力能够验证到什么程度。

必须通过真实代码和可复现证据支持审计结论。

1.2 视觉探索与生产实现分离

本阶段不得大规模修改生产页面，不得为了展示新风格而直接覆盖全局 WXSS、公共组件或现有业务模板。

实验代码应优先放在独立的实验目录或独立 worktree 中。

如果需要创建独立分支，先检查仓库状态和并发开发约定，再选择合适的隔离方式。

如果现有工作区存在未提交修改、其他 Agent 正在开发、分支落后或存在冲突风险：

1. 不覆盖、不清理、不重置他人的改动。
2. 不在共享工作区直接开展大规模视觉实验。
3. 优先创建独立 worktree，或使用不会影响生产代码的实验目录。
4. 在实验开始前记录基线 commit、工作区状态和实验产物位置。

不得擅自执行破坏性 Git 操作。

1.3 不虚构项目能力

原型必须清楚区分真实业务数据、固定演示数据和模拟交互。

可以使用固定的演示数据来比较视觉效果，但不得将未实现的功能标记为已经接通真实后端。

不得为了展示设计而擅自更改业务规则、接口契约、用户身份逻辑、权限逻辑或既有测试基线。

2. Phase 0：建立项目基线

开始时先完成以下工作。

2.1 仓库与并发状态检查

记录：

- 仓库路径、当前分支、HEAD commit。
- 工作区是否干净。
- 是否存在未提交改动、未跟踪文件和并发开发痕迹。
- 当前分支与远端目标分支的关系。
- 现有测试命令、构建命令和开发者工具运行方式。

如果检测到其他 Agent 的工作，不要试图把工作区恢复成干净状态；应当隔离实验。

2.2 页面与组件盘点

从实际路由、页面注册和源文件出发，建立页面清单。

至少记录：

字段| 内容
页面名称| 真实页面名称
路由| 真实路由
用户任务| 用户在此页面完成什么
核心信息| 必须展示的数据与状态
核心交互| 主要操作与结果
共享组件| 实际复用的组件
当前视觉问题| 以代码或页面证据为依据
重构风险| 涉及哪些业务状态和逻辑
验收方式| 如何验证视觉和行为

覆盖整个小程序，而不是只查看首页。

2.3 当前 UI 的 Demo 化诊断

请重点检查以下问题，但不要预设它们一定存在：

- 页面是否普遍使用相同的圆角卡片容器。
- 是否存在无意义的渐变、阴影、描边和装饰性图标。
- 标题、正文、辅助信息的字号和字重是否缺乏层次。
- 留白是否只是为了视觉装饰，而非服务信息分组。
- 状态标签是否过多，颜色是否滥用。
- 图片是否与真实户外活动相关，裁切和色调是否一致。
- 关键行动按钮是否与次要操作争夺注意力。
- 表单、成员列表、车辆分配等工具型页面是否被设计得过于营销化。
- 天气、地图、位置共享等页面是否缺少必要的信息密度和专业性。
- 是否存在组件重复、样式覆盖、硬编码颜色和难以维护的全局规则。

每项问题应尽可能关联具体页面、文件、组件或截图。

2.4 输出基线报告

创建独立实验文档，至少包含：

- "visual-direction-lab-baseline.md"
- 页面与组件清单。
- 当前 UI 问题清单。
- 现有业务逻辑保护清单。
- 实验环境和运行方式。
- 当前测试基线及其已知限制。

以上文件应写入独立实验目录或实验分支，不要擅自向生产目录添加大量临时文档。

完成基线检查后，进入下一阶段，不必等待人工确认；但如果发现无法安全隔离的并发冲突、关键运行环境缺失或实验将影响生产代码，应先停止相关操作，并明确报告阻塞原因。

3. Phase 1：设计五套有明确差异的视觉方向

建立五个独立的候选风格。它们必须在视觉语言、信息组织和品牌气质上存在实质差异，而不是只替换主题色。

Style A：Alpine Editorial

定位：精品户外品牌、山野编辑部。

关键词：克制、自然、精致、编辑感。

设计探索方向：

- 自然纸白、深森林绿、岩石灰构成基础色彩。
- 清晰的标题梯度和富有节奏的留白。
- 通过摄影、排版和内容层级建立品牌感。
- 适度使用大图，但避免所有页面都使用大面积封面。
- 活动信息采用清晰的内容分组，而不是层层套叠的卡片。

预期优势：品牌感突出，适合活动发现、俱乐部和路线内容。

潜在问题：如果过度强调编辑感，可能影响高频协作操作的效率。

Style B：Swiss Functional

定位：现代功能主义。

关键词：网格、秩序、精确、克制。

设计探索方向：

- 强调排版、对齐、信息分组和严格的间距体系。
- 使用有限的品牌色与状态色。
- 减少装饰性阴影和容器。
- 用分隔线、留白、文字权重和位置关系组织信息。
- 操作按钮与信息展示之间具有明确的层级。

预期优势：组件复用性强，适合复杂表单、成员管理和车辆分配。

潜在问题：容易缺乏户外品牌温度。

Style C：Quiet Terrain

定位：安静、自然、成熟的户外生活方式产品。

关键词：低饱和、自然材质、温和、长期耐看。

设计探索方向：

- 以岩石、苔藓、雾气、自然纸张等色彩感受为灵感。
- 使用温和但具有对比度的色彩。
- 减少视觉刺激，注重正文阅读体验。
- 使用细腻的分隔、轻量的状态表达和自然的内容节奏。
- 不使用拟物材质效果来假装高级。

预期优势：耐看、友好，适合广泛的户外用户群体。

潜在问题：如果对比度不足，容易显得平淡或降低信息辨识度。

Style D：Field Instrument

定位：专业户外工具。

关键词：地形、数据、导航、可靠性。

设计探索方向：

- 使用明确的地理信息和数据排版。
- 重点探索海拔、距离、集合点、天气窗口和路线状态的视觉表达。
- 等高线、地图纹理等元素仅在具有功能或品牌价值时使用。
- 让关键状态可扫描、可比较、可快速理解。
- 不把每个数据项都包装成仪表盘小卡片。

预期优势：适合天气、路线、地图和活动协作页面。

潜在问题：可能过于技术化，不适合作为全站唯一的视觉语言。

Style E：Expedition Modern

定位：现代远征品牌。

关键词：行动力、户外装备、鲜明排版、有限的强对比。

设计探索方向：

- 使用岩石深色、自然浅色和有限的强调色。
- 强调路线编号、活动状态和明确的行动入口。
- 通过标题、网格和信息密度建立力量感。
- 不依赖黑底橙色的套路，也不模仿游戏 HUD。
- 确保日常徒步和轻户外活动同样适用。

预期优势：辨识度高，适合高海拔徒步和远征场景。

潜在问题：容易显得过于严肃或具有攻击性。

风格实验的共同约束

五套风格必须使用：

- 相同的业务内容。
- 相同的演示数据。
- 相同的核心操作。
- 相同的页面尺寸和测试场景。
- 尽可能相同的内容长度与图片素材。

不要通过减少内容、隐藏操作或降低信息密度，让某套风格获得不公平的视觉优势。

如果上述风格与当前项目实际情况存在冲突，可以在基线报告中提出修订建议，但不要擅自把五套风格合并成五个仅有颜色差异的主题。

4. Phase 2：制作可运行的多风格原型

这是本阶段的核心交付。

4.1 原型形态

建立一个独立的 UI 原型入口，至少支持：

- 五套风格之间切换。
- 在相同页面上比较不同风格。
- 展示每套风格的颜色、字体、间距、圆角和主要组件。
- 运行真实的页面交互演示。
- 在不同常见手机视口尺寸下查看布局。
- 通过统一的数据源比较相同内容的呈现效果。

如果仓库现有技术栈适合直接在微信小程序环境中构建原型，优先使用现有技术栈和项目组件体系。

如果当前页面体系不适合快速实现隔离实验，可以采用独立的静态或 Web 原型，但必须说明它与真实小程序之间的差异，并为后续真机验证保留明确的验收任务。

不得仅生成五张静态截图就宣称完成了可运行原型。

4.2 代表页面

至少实现以下三个代表性页面。

页面一：活动发现

用于评估品牌感、摄影、信息层级和活动浏览体验。

展示真实业务语义，包括：

- 活动名称和目的地。
- 出发日期。
- 行程或路线概况。
- 费用信息。
- 领队信息。
- 剩余席位或活动状态。
- 进入详情或报名的主要操作。

页面二：活动详情

用于评估长内容、活动信息组织和决策体验。

展示：

- 活动介绍与行程。
- 出发地点和时间。
- 费用、要求和注意事项。
- 领队与参与者信息。
- 报名、加入或退出等对应的操作状态。

必须基于现有项目的实际功能设计。若某项功能当前不存在，不得伪装成已经实现。

页面三：活动协作

用于评估高信息密度和工具型交互。

优先考虑项目现有的集合点、成员、车辆与座位分配等能力。

重点展示：

- 活动当前状态。
- 集合点和关键时间。
- 成员信息。
- 车辆和座位状态（如果现有功能支持）。
- 需要用户完成的下一步操作。
- 操作成功、失败、禁用和空状态。

如果实际项目的页面结构不同，应根据代码审计结果选择对应的真实页面，不得为了满足文档而虚构新业务。

4.3 天气和地图作为扩展验证页

如果上述三个页面完成后仍有充足时间，再增加天气或地图页面作为第四个验证场景。

原因是：发现页和详情页更容易表现品牌感，但无法充分验证工具型页面的信息密度。

天气页面应保留必要的时间、天气、海拔或路线语义。地图页面应区分地理内容、状态信息和操作控件。

若天气或地图页面尚未具备完整的真实数据能力，可使用明确标记的固定演示数据进行视觉实验。

4.4 交互要求

至少实现：

- 风格切换。
- 页面切换。
- 主要按钮反馈。
- 关键状态切换。
- 空状态、错误状态或禁用状态中的适当示例。
- 长内容滚动和不同视口下的布局验证。

所有交互应有可观察的结果。

不要求在风格实验阶段重新实现后端接口、真实定位或完整的业务流程。

4.5 设计令牌

为每套风格建立独立且结构一致的令牌定义。

至少包含：

- "color.background"
- "color.surface"
- "color.text.primary"
- "color.text.secondary"
- "color.border"
- "color.brand"
- "color.action"
- "color.success"
- "color.warning"
- "color.danger"
- "typography.title"
- "typography.body"
- "typography.caption"
- "spacing"
- "radius"
- "shadow"
- "icon"
- "motion"

实际命名可以服从项目现有约定，但必须有统一的映射关系。

不能让组件直接散落硬编码颜色。切换风格时，应当由主题令牌驱动主要视觉变化。

同时避免为了追求抽象而建立庞大、难以理解的主题引擎。先满足本轮实验需求，再决定是否值得引入更复杂的架构。

4.6 原型交付物

建议建立如下结构；如项目已有约定，允许调整路径，但必须保持实验隔离。

"docs/ui-design/visual-direction-lab/"

- "README.md"：原型运行、切换、测试和查看方法。
- "baseline.md"：现状审计。
- "style-directions.md"：五套风格的定义和差异。
- "design-tokens.md"：令牌设计。
- "evaluation.md"：评审标准和实际结果。
- "production-migration-plan.md"：后续生产重构计划。

独立原型目录：

- 原型入口。
- 五套主题定义。
- 代表页面。
- 公共演示数据。
- 交互状态。
- 运行和验证脚本（如适用）。

应当使用清晰的目录边界，禁止把实验专用的样式、数据和组件意外引入生产入口。

5. Phase 3：视觉质量与产品感验收

不要仅以“看起来更好看”作为验收标准。

5.1 建立统一评审基准

对五套风格分别评估以下维度：

维度| 权重
真实产品感，是否摆脱 Demo 化| 25%
信息层级与可读性| 20%
户外品牌辨识度| 20%
视觉完成度与一致性| 15%
小程序适配与操作体验| 10%
组件复用和长期维护性| 10%

每项使用 1–5 分，并给出具体证据和扣分原因。

总分可按权重换算为百分制，但分数不能代替实际页面对比和设计判断。

5.2 强制检查的视觉问题

逐项检查：

- 是否所有内容都被包进圆角卡片。
- 是否滥用渐变、阴影、描边和装饰性元素。
- 标题、正文、辅助信息之间是否存在明确的视觉层级。
- 是否有足够但不过量的留白。
- 图片是否具有统一的摄影和裁切规则。
- 品牌色是否被过度使用。
- 重要操作是否足够突出。
- 标签、图标和状态颜色是否存在语义混乱。
- 内容较长时，布局是否依然清晰。
- 空状态、错误状态和禁用状态是否具有明确表达。
- 页面是否过度依赖大图来制造精致感。
- 页面是否只是把旧版组件换色，而没有改善信息组织。

5.3 实际运行与视觉证据

必须尽可能运行原型并检查实际渲染结果。

如果使用微信小程序原型，应优先使用项目现有的开发者工具和自动化验证能力。

如果使用 Web 原型，应至少检查常见手机宽度、长内容、交互状态和滚动行为，并明确说明这些结果不能替代微信小程序真机验收。

输出：

- 各风格代表页面截图。
- 同页面五风格对照。
- 各风格评分及评分依据。
- 已发现的布局或交互问题。
- 尚未验证的场景。

不能只报告构建成功或测试通过，就认定视觉质量已经达标。

5.4 选择规则

建议优先选择一个主风格，而不是把五套风格同时保留为生产主题。

可以采用以下组合思路：

- 主品牌方向：Alpine Editorial 或 Quiet Terrain。
- 信息组织原则：Swiss Functional。
- 地图、天气与路线等专业页面：适度采用 Field Instrument 的表达方式。
- Expedition Modern 作为对比方案，验证品牌是否需要更强的行动感。

这只是初始假设，不是预先决定的最终结论。

最终主风格必须由真实原型、实际页面表现和评审证据决定。

---

6. Phase 4：输出全局设计系统与逐页重构计划

本阶段只制定生产迁移方案，不执行大规模生产重构。

6.1 全局设计系统

基于胜出的风格，形成：

1. 品牌色与语义色规范。
2. 字体、字号、字重和行高规范。
3. 间距与布局规范。
4. 圆角、边框、阴影规范。
5. 图标和图片规范。
6. 按钮、输入框、列表、状态标签等基础组件规范。
7. 活动卡片、成员信息、集合点、车辆和座位等业务组件规范。
8. 空状态、错误状态、加载状态与禁用状态规范。
9. 页面层级与导航规范。
10. 亮色和暗色模式策略（仅在项目实际需要时纳入）。

不要为了建立统一设计系统而强迫所有页面使用完全相同的布局。统一的是视觉规则和交互原则，而不是每个页面的结构。

6.2 页面重构顺序

根据实际审计结果，提出分批重构顺序。

建议优先级：

- P0：基础设计令牌和共享组件。
- P1：活动发现、活动详情等高曝光页面。
- P2：活动协作、集合点、成员和车辆等高频工具页面。
- P3：天气、地图、位置共享等专业信息页面。
- P4：个人页面、次要流程和低频页面。

实际优先级应根据现有页面数量、组件依赖、业务风险和用户使用频率调整。

6.3 每批生产重构的边界

后续真正实施时，每批都必须：

- 有明确页面范围。
- 有明确的业务逻辑保护清单。
- 复用已冻结的设计令牌和组件规范。
- 进行视觉对照和行为回归。
- 保持接口、数据结构和权限语义不变，除非另行授权。
- 记录已完成、未完成和无法验证的事项。
- 避免多个 Agent 并发修改相同的全局样式和公共组件。

当前任务不得擅自进入这些生产重构批次。

7. 自动化与回归保护

在视觉实验过程中，先识别并复用项目现有的测试体系，不要另起一套与项目脱节的验证框架。

必须保护的方面

- 页面路由和页面注册。
- 现有用户身份与授权流程。
- 活动创建、加入和退出等已有流程。
- 成员、领队和活动状态。
- 车辆与座位分配等已有业务。
- 位置共享和天气相关的现有数据契约。
- 表单校验、权限限制、错误反馈和禁用状态。
- 现有测试基线与并发开发改动。

上述清单需要根据实际仓库进行修订，不能把不存在的功能描述为现有能力。

验收层级

1. 静态检查：实验代码是否越界进入生产目录，是否有不必要的依赖或硬编码。
2. 构建检查：原型是否能够正常构建和启动。
3. 交互检查：页面切换、主题切换、按钮和状态演示是否有效。
4. 视觉检查：各代表页面在目标视口下是否符合设计规则。
5. 生产隔离检查：实验是否影响真实页面、路由、接口和共享组件。
6. 回归检查：若隔离环境仍与生产代码共享部分模块，必须确认没有破坏既有功能。

对于平台限制、无法自动化验证的场景，应明确记录为未验证，不能把它们记为通过。

8. Agent 协作方式

可以根据实际任务拆分给多个 Agent，但必须先明确隔离边界。

Agent A：代码与视觉审计

负责：

- 仓库基线检查。
- 页面和组件清单。
- 当前视觉问题诊断。
- 业务逻辑保护清单。
- 实验隔离建议。

不得修改生产页面。

Agent B：风格研究与令牌设计

负责：

- 五套风格定义。
- 色彩、字体、间距和组件规范。
- 风格之间的差异说明。
- 各风格适用页面与风险分析。

不得修改生产页面。

Agent C：多风格原型实现

负责：

- 独立原型。
- 主题切换。
- 代表页面。
- 统一演示数据和基础交互。
- 原型运行文档。

必须在隔离环境内实施。

Agent D：视觉评审与质量验证

负责：

- 实际运行原型。
- 截图与同页对照。
- 视口和交互检查。
- 评分和问题清单。
- 对设计方案提出可验证的修改建议。

不得通过修改生产代码来绕过原型问题。

如果只有一个 Agent 执行，则按上述顺序串行推进。

如果多个 Agent 并行，则各自使用独立 worktree 或清晰分离的文件范围。不得让多个 Agent 同时修改同一个原型入口、共享主题文件或全局样式。

11. 执行与汇报要求

请直接开始执行，不要先向我重复解释设计理念，也不要只给我一份计划后等待确认。

首先完成基线审计，再建立隔离的实验环境，然后实施五套风格和可运行原型。

在实现过程中，优先保证实验的真实性、可比较性和可复现性。

遇到非关键问题时，根据仓库实际情况作出合理决策，并在报告中记录。遇到可能破坏生产代码、覆盖并发改动、影响业务数据或无法安全隔离的重大问题时，应停止相应操作并说明原因。

最终汇报请按照以下顺序：

1. 实际完成了什么。
2. 原型在哪里，如何运行。
3. 五套风格的真实差异。
4. 视觉对照和评分结果。
5. 最推荐的主风格及证据。
6. 生产代码是否受到影响。
7. 测试、验证和未验证事项。
8. 后续全局设计系统与逐页重构方案。

本轮的成功标准不是改动文件数量，也不是页面截图是否足够华丽。

真正的成功是：我们获得了一套可以运行、可以比较、可以复现的视觉实验环境，并且能够基于实际证据决定 OurTrail 接下来应该采用什么样的设计语言。

先建立选择正确风格的能力，再开始大规模重构。
