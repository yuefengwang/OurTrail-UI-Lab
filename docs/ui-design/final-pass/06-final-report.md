## 1. 四个页面各自解决了哪些最重要的问题

### 发现页
- **从“杂志封面”变成发现入口**：主推首屏给出最近一场、集合时间、余位/截止、距离/爬升/难度/人均、领队与适合人群，唯一 CTA「查看安排」。
- **375 首屏主行动可见**：主 CTA 底边 471 < 页面可用高度 603（Round 4 为 616–664，按设备 667 误判为可见）。
- **索引效率**：默认未来在前、过去折叠；默认排除主推；搜索/筛选才返回完整结果；首行在 375 露出 16px、390 完整可见。
- **去噪**：接缝带 134→紧凑筛选条；整卡按钮→单一 CTA；1:1 裁切→4:3 + focus；长标题拆“2 日”标签。

### 详情页
- **从信息堆叠变成决策路径**：状态/下一步 → 身份 → 决策事实 → 适合谁/风险 → 路线/集合 → 行程 → 准备 → 领队/我的安排 → 费用/退出。
- **主行动唯一且随状态变化**：未报名/待审核/已确认/候补/取消/关闭/归档/组织者，各自只有一个主 CTA；天气从主按钮降为路线区入口。
- **路线可理解**：数据驱动 SVG 地图 + 海拔剖面 + 3 个节点 + 2 个上车点 + 活动日天气入口；标注“路线示意 · 非导航”。
- **权限/隐私**：参与者不再看到“全量名单/分车/电话尾号/他人座位”；全量名单只进协作工作台。
- **报名/名单本地事务化**：提交后进入协作名单，审核通过回写详情，取消释放名额；发现/详情/协作计数同步，不再停留在快照口径（仍是内存事务，不是后端）。

### 协作页
- **从组件顺序变成任务顺序**：首屏是阶段、倒计时、准备度与「审核报名 3 / 安排车辆 1 / 报名今晚截止」；唯一主操作从 2585px 移到首屏 329–389。
- **真实车辆口径**：不再 4×4 统一格；1 号中巴 18 乘客位、2 号车 6 乘客位、司机不占乘客座、自行前往/未分配单列。
- **可执行**：审核通过/拒绝、逐人分车、签到、异常处理、逐人确认到家、阶段推进均有真实结果；完成后计数/队列/面板即时更新。
- **阶段与角色**：行前→集合→同行→返程→归档的门槛写清楚；组织者/协作/车长三套视角；车长只本车 10 人，不看全量名单/敏感资料。

### 天气页
- **从单点天气卡变成路线天气工具**：活动窗口 × 3 个路线点（780/1060/1240m）× 云底/海拔 × 降水/风/温度。
- **回答“哪段、什么时候值得关注”**：低云·石阶湿滑（06:00–10:00）、阵雨·风增大（12:00–17:00）、雨势减弱（17:00–19:00）；建议 12:30 前通过白云索道段。
- **数据诚实**：页头常驻“模拟预报 · 非真实气象服务”；范围/生成时间/海拔来源/限制/行动边界常驻；无数据不插值。
- **375 专用布局**：完整图表 + 图例进入 603px 首屏（272–601）；风放到选中详情，距离/爬升与 summary 次要说明在 375 收起，模拟徽标与限制仍在。
- **可从详情进入并返回**，活动名/路线点/时间不丢。

## 2. 哪些设计决定来自真实产品业务，而不是审美偏好

| 设计决定 | 业务依据 |
|---|---|
| 发现默认未来在前、过去置底/折叠 | 用户先找“现在能报名/最近出发”；过去活动不是本轮任务 |
| 详情主 CTA 随 12 态变化 | 真实 `getDetailState` / `participantNext`；不同状态下一步不同 |
| 待审核占名额、候补不占名额 | `remaining = capacity − confirmed − pending`；`selectors.ts` |
| 详情不出现全量名单/敏感资料 | 真实权限：参与者只看本人/代报名同行人；敏感资料需用途 |
| 协作任务优先、阶段门槛 | `leaderQueue` + `activity.ts` 阶段推进条件；published→gathering 不能有 pending；closing→archived 必须全员到家 |
| 车辆真实核载、司机不占乘客座、上车点覆盖 | `allocation.ts` / `transport.ts` / `invariants.ts` |
| 签到 ≠ 上车；发车完成 ≠ 到家 | `field.ts` 独立履约事实；车长只看本车两程 |
| 天气绑定活动窗口/路线点/海拔 | P1–P4 天气文档；`routeSnapshot.points` + `ele` + `time` |
| 模拟标注、无绝对安全结论 | 产品明确“预报不是出发许可”，免费版无实况/雷达 |
| 报名 sheet 必填紧急联系人/三项授权 | `Signup.tsx` 真实字段与授权边界 |
| 费用只说明、不收款 | 真实产品无支付/退款；`feeNote` 只是线下结算 |
| 详情只允许组织者进工作台 | `ownerId` / `permissions.ts` |

审美偏好只决定“怎么好看”；上面这些决定决定“能不能用”。

## 5. 这套设计如何迁移到正式 OurTrail 微信小程序

**顺序**：token/全局组件 → 发现 → 详情 → 协作 → 天气 → 跨页/真机。

- **事务映射**：本地 `store.actions` 必须映射到真实 `signup.submit/review/promote/cancel`、`transport.assign/board/depart`、`attendance.checkin/home`、`incident.resolve`、`activity.advance`；客户端只做提示，服务端事务与门槛最终裁决。

- **发现**：`pages/discover` + `ActivityHome/ActivityCard`；消费窄投影，不返回名单/集合点/敏感字段。
- **详情**：`pages/activity` + `ActivityDetail`；用 `getDetailState`/`participantNext`/`permittedActions`；报名走 `pages/signup`；路线用 `routeSnapshot.points/track` + 真实地图组件；无坐标不画假地图。
- **协作**：`pages/workspace` + `Workspace/Roster/Transport/Field/VehicleTask`；任务用 `leaderQueue`；车辆用 `allocation/transport/invariants`；现场用 `field`；角色用 `permissions` 的 capability/scope/expiry；阶段用 `activity.ts` 服务端门槛。
- **天气**：`pages/weather-hub` / `pages/weather`；用 routeSnapshot points + `getWeather` + `weather-model` + `sky.js`；Open-Meteo 真实数据；canvas 2D DPR 绘制，不嵌 SVG；保留范围/来源/限制/降级。
- **不做**：支付/退款、实时追踪、IM、救援承诺；不把模拟天气/演示名单/AI 图带进生产。

详细映射、数据契约、依赖、风险与测试计划见 [05-production-handoff.md](./05-production-handoff.md)。

## 6. 为什么可以认为本轮已经足以作为正式改版的设计基准

因为交付的不是“四张更漂亮的页面”，而是：

1. **真实业务映射**：7 活动阶段、6 报名状态、12 参与者详情状态、权限/车辆/现场/天气模型都有来源与边界。
2. **可执行的页面结构**：发现能比较、详情能决策、协作能执行、天气能判断；不是四套互不相干的模板。
3. **可测量的改进**：375 发现 CTA 471/603；375 天气完整图表 272–601；协作主任务 2585→329；默认重复活动 3→1；0 横向溢出/0 console error；56+39+49 项回归。
4. **跨页同源**：活动/路线/时间/费用/名额/领队/路线点/天气窗口由单一数据源派生；X1–X10 通过；报名→协作→审核→详情→发现→取消的 S12–S24 事务链通过。
5. **可迁移的系统**：token、组件、状态语义、图表规格、文案规则、迁移顺序与风险都已写成文档；生产可以直接按 04/05/07 落地。
6. **诚实的遗留清单**：没有宣称“全部达标”；非主活动数据、真实天气、物理真机/AI 图、本地事务与后端的差距都明确列为未完成或需替换。

**最终判定**：可以作为正式改版的**设计基准**；不能作为“已经完成生产实现”的证明。下一步应把本地事务映射到真实命令并做物理真机/微信开发者工具验收，再进入正式小程序开发。
